# FPS камеры и граббера: аппаратный эксперимент 2026-11-13

Камера **MV-AX5F57MP050E**, серийный номер FG06273AAK00001; граббер
**Magewell Flex I/O Quad CXP-12 Enhanced**, линк **CXP12_X4**.
Все измерения — **Mono8**, Continuous, TriggerMode Off, без ограничения
AcquisitionFrameRateEnable, OffsetX/OffsetY = 0. Проверены захват без
копирования (`discard`) и memcpy каждого кадра в переиспользуемый RAM-буфер
(`copy`). Кадры на диск не записывались; все кадры съёмки в RAM не накапливались.

## Главные результаты

- Плато около **199 кадров/с при выдержке 5000 мкс** подтверждено.
- При сокращении высоты и выдержки связка достигает **около 12 270 кадров/с**
  на минимальной высоте **2 строки**, включая memcpy в RAM.
- Уменьшение ширины **9344 → 4672** на сопоставленных режимах без тормозящей
  диагностики устойчивого повышения FPS не дало. Оно уменьшает объём данных и нагрузку на память.
- В штатном `bench` обнаружен сильный эффект измерительного кода:
  `scap_get_data_stream_info` на каждом кадре резко снижает скорость и может
  вызывать потери. Увеличение очереди с 8 до 64 буферов проблему не устранило.
- Для корректного измерения предела использована отдельная сборка с отключённым
  только покадровым опросом stream info. Штатные исходники и бинарники не менялись.

## Эмпирическая формула

Для измеренных режимов Mono8 с ширинами 9344 и 4672 результаты хорошо
описываются формулой (все времена в микросекундах):

```text
T_readout ≈ 2 × Height + 77,5
T_exposure ≈ ExposureTime + 24,6
FPS ≈ 1 000 000 / max(T_readout, T_exposure)
```

Это модель по замерам конкретной камеры/прошивки, а не паспортная гарантия.
Её нельзя автоматически переносить на Mono10/Mono12, другие ширины,
многозонный ROI, binning, внешние триггеры и другие режимы сенсора.
Она описывает непрерывную съёмку с перекрытием выдержки и считывания.

Проверка периода считывания на полной ширине:

| Высота | Период из измеренного FPS, мкс | Период минус 2×Height, мкс |
|---:|---:|---:|
| 7000 | 14077,27 | 77,27 |
| 2500 | 5077,49 | 77,49 |
| 1000 | 2077,54 | 77,54 |
| 500 | 1077,52 | 77,52 |
| 16 | 109,50 | 77,50 |
| 2 | 81,50 | 77,50 |

При выдержке 5000 мкс плато начинается примерно ниже **2474 строк**:
период становится около 5024,6 мкс, то есть 199,02 кадра/с. На 2500 строках
считывание ещё даёт 5077,5 мкс, то есть 196,95 кадра/с.
При выдержке 1000 мкс предел от выдержки около 975,94 кадра/с;
при 100 мкс — около 8022 кадров/с. На 2 строках достаточно выдержки
примерно 57 мкс или короче для достижения предела считывания около 12 270 кадров/с.

Один 3-секундный прогон 9344×16, 100 мкс, discard дал 8558,79 кадра/с
и выбивается из модели. Причина отдельно не установлена. Сопоставимый copy
дал 8022,39, а измерения 8 и 4 строк при той же выдержке и оба режима на
половинной ширине дали около 8022 кадров/с. Выброс не использован для формулы.

## Почему штатный bench давал неправильное представление о пределе

В `src/main.cpp` внутри цикла каждого кадра вызывается
`scap_get_data_stream_info`. В SDK этот вызов делает шесть запросов
`DSGetInfo`. Контрольная сборка отключает только этот вызов; получение кадров,
чтение их метаданных, подсчёт frame_id, измерение времени и memcpy сохранены.

Пример 9344×1000, 27 мкс:

| Вариант | discard, кадров/с | copy, кадров/с |
|---|---:|---:|
| Штатный, 8 DMA-буферов | 153,69, с потерями | 123,08, с потерями |
| Штатный, 64 DMA-буфера | 129,98, с потерями | 88,73, с потерями |
| Без покадрового stream info, 8 DMA-буферов | 481,34, без потерь | 481,35, без потерь |

Поэтому результаты штатного bench на малых ROI нельзя считать пределом
сенсора или пропускной способности memcpy. Показатель `source_fps` при
потерях вычисляется по номерам кадров и времени хоста; он не заменяет
фактический FPS принятого потока. При остановках потока отсутствие дыр
в frame_id тоже не доказывает достижение предела камеры.

## Методика и воспроизведение

Большинство прогонов: окно 3 с, прогрев 16 кадров, 8 DMA-буферов,
один прогон на комбинацию. Контроль глубины очереди: 64 DMA-буфера.
Для проверки максимума предусмотрены повторы по 10 секунд, с чередованием
порядка discard/copy между повторами. Конкретные параметры каждого набора
есть в `config.json`, фактические интервалы и пропуски — в сырых отчётах.

Исходный код приложения: git `c7f2cf444b5b53146e2003fc5d048e858efb7a76`.
Контрольная сборка: g++ C++17, `-O2`, библиотека SDK `build/easycap.a`;
изменённая копия main.cpp находится в `/tmp/grabercam-fps-probe-20261113`.
Скрипт сборки позволяет воспроизвести её после удаления временного каталога.

```bash
python3 scripts/build_bench_probe.py --out /tmp/grabercam-fps-probe-new
python3 scripts/sweep_fps.py \
  --binary /tmp/grabercam-fps-probe-new/grabercam-probe \
  --out experiments/recheck \
  --widths 9344 4672 --heights 2500 1000 500 100 16 8 4 2 \
  --exposures 5000 1000 100 27 --seconds 3
python3 scripts/report_fps.py experiments/recheck
```

Скрипт сохраняет исходные настройки, проверяет запись параметров чтением,
сохраняет результаты после каждого прогона и восстанавливает настройки
при завершении и ошибках. Проверены восстановление при отказе настройки
и SIGTERM, а также генерация отчётов: 3 автоматических теста прошли.

Исходные настройки сессии: **9296×796, Mono8, ExposureTime=2300 мкс,
OffsetX=OffsetY=0, TriggerMode=Off, Continuous, AcquisitionFrameRateEnable=0**.

## Повторы максимума и восстановление настроек

| Ширина | Режим | Повтор 1, кадров/с | Повтор 2, кадров/с |
|---:|---|---:|---:|
| 9344 | discard | 12269.87 | 12269.84 |
| 9344 | copy | 12269.87 | 12269.85 |
| 4672 | discard | 12269.86 | 12269.83 |
| 4672 | copy | 12521.29 | 12269.87 |

Каждый прогон — 10 секунд, Height=2, ExposureTime=27 мкс; во всех 8 прогонах
пропуски frame_id, скачки назад и таймауты равны нулю. Один прогон на
половинной ширине дал 12521,29 вместо обычных 12269,9 кадра/с; причина этого
отклонения отдельно не установлена. Повтор его не воспроизвёл, поэтому
устойчивое повышение FPS от сокращения ширины не подтверждено.

Всего выполнено **200 успешных измерительных прогонов**. После всех серий,
включая отказ настройки Height=1, восстановление исходных настроек
подтверждено чтением (`status.json`). На отказе SDK не завершил текст ошибки
переводом строки, из-за чего ранняя версия скрипта записала TimeoutError;
разбор ответа исправлен и покрыт тестом. Сообщение самого SDK в журнале
однозначно указывает минимум Height=2.
