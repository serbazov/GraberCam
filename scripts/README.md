# Проверка FPS камеры

Запускать из корня проекта при свободной камере, без live preview:

```bash
python3 scripts/sweep_fps.py --out experiments/my-run
python3 scripts/report_fps.py experiments/my-run
```

Нужны Python 3, `stdbuf`, собранный `grabercam` и установленный SDK Magewell.
SDK должен иметь доступ к устройству и своему журналу `/var/log/magewell`.
Скрипт не требует Python-пакетов из pip.

По умолчанию проверяются ширины 9344 и 4672, высоты 7000, 2500, 1000,
500, 100 и 16, выдержки 5000, 1000, 100 и 27 мкс. Каждая комбинация
проверяется 3 секунды отдельно в `discard` и `copy`, с 16 кадрами прогрева
и 8 DMA-буферами. Время прогрева входит в заданное окно, но не в расчёт FPS;
на большой выдержке для точности нужен более длинный прогон.

Пример повторных замеров с увеличенной очередью:

```bash
python3 scripts/sweep_fps.py --out experiments/repeat \
  --widths 9344 4672 --heights 1000 500 100 16 \
  --exposures 1000 100 27 --seconds 5 --repeats 3 --buf 64
python3 scripts/report_fps.py experiments/repeat
```

Скрипт сохраняет текущие ROI, формат, выдержку, режим съёмки, триггер и
переключатель ограничения FPS. На время проверки выбирает Mono8, Continuous,
TriggerMode Off, отключает ограничение FPS и обнуляет смещения ROI. После
обычного завершения, ошибки, Ctrl+C или SIGTERM восстанавливает настройки
и проверяет их чтением. После принудительного завершения SIGKILL или аварии
процесса настройки нужно восстановить вручную по `initial.json`.
Пользовательские профили камеры и прошивка не записываются.

Параметры проверяются чтением после каждой записи; неподдерживаемые значения
останавливают эксперимент. Используется одна shell-сессия, чтобы не
переподнимать CXP-линк между измерениями. Каждый прогон имеет отдельный JSON;
существующий каталог результатов не перезаписывается. `results.json`
обновляется после каждого завершённого прогона. `status.json` содержит
ошибки и результат восстановления, `session.log` — полный вывод SDK,
`config.json` — параметры скрипта. `report_fps.py` можно запускать и на
незавершённой серии: он создаёт таблицы Markdown и CSV без изменения замеров.

`copy` копирует каждый кадр в один переиспользуемый буфер RAM; это проверка
пропускной способности memcpy, а не накопление всей записи в оперативной памяти.
Основная метрика — `delivered_fps`. `source_fps` восстанавливается по номерам
кадров и времени хоста, поэтому при больших потерях или остановках потока
не следует считать его точным пределом сенсора. Проверяйте также `dropped`,
`disorder`, `timeouts`, интервалы кадров и состояние очереди DMA.
Показанный SDK timestamp сам по себе не гарантирует время экспонирования.

Изменение размера DMA-очереди меняет потребление памяти: примерно
`Width × Height × число буферов` байт для Mono8, плюс накладные расходы SDK.

## Контроль влияния диагностики

В штатном `bench` на каждом кадре вызывается `scap_get_data_stream_info`,
а SDK внутри делает несколько вызовов GenTL. Для отдельного A/B-замера
можно собрать вариант, в котором отключён только этот опрос:

```bash
python3 scripts/build_bench_probe.py --out /tmp/grabercam-fps-probe
python3 scripts/sweep_fps.py --binary /tmp/grabercam-fps-probe/grabercam-probe \
  --out experiments/no-stream-stats --widths 9344 \
  --heights 1000 500 16 --exposures 1000 27
python3 scripts/report_fps.py experiments/no-stream-stats
```

Сборка использует исходники проекта и `build/easycap.a`, сохраняет изменённую
копию `main.cpp` в указанном новом каталоге. Исходники и штатные бинарники
не меняются. Метаданные кадров, учёт пропусков и memcpy сохраняются.
В экспериментальной сборке нет статистики свободных DMA-буферов; отсутствие
этого поля в JSON ожидаемо. Этот вариант нужен для сравнения, его результаты
нужно хранить отдельно от замеров штатного приложения.

Проверка протокола скрипта, восстановления при ошибке и SIGTERM без камеры:

```bash
python3 -m unittest discover -s tests -v
```

В аппаратном эксперименте 2026-11-13 покадровый опрос действительно сильно
искажал результат: 9344×1000 при 27 мкс в штатном `discard` принимал около
154 кадров/с с потерями, а вариант без этого опроса — 481 кадр/с без потерь.
На ROI 9344×2 вариант без опроса достиг около 12 270 кадров/с в `discard`
и `copy`. Для измерения предела камеры используйте контрольную сборку,
а штатную — для оценки поведения текущего приложения. Полные результаты
и ограничения приведены в [отчёте](../experiments/2026-11-13-fps.md).

# Переключение четырёх ROI

Этот эксперимент использует нативный C++-цикл, чтобы не включать Python,
разбор shell-команд и повторное открытие камеры в задержку переключения.
Координаты — OffsetY 0, 1750, 3500, 5250 при OffsetX=0, выдержке 300 мкс,
Mono8 и размере 7008×1750. Камера округляет ширину 7000 до 7008; её шаг — 16.

Основная серия: статичные зоны для калибровки, время записи координаты,
пауза SDK, полный перезапуск захвата, переключение с подтверждением по
изображению и независимый поток управления каждые 1/4/16 кадров:

```bash
python3 scripts/run_roi_switch.py --out experiments/roi-switch-my-run
```

Длинная проверка переключения каждые 2 и 4 кадра (по 4096 кадров на режим):

```bash
python3 scripts/run_roi_switch.py --out experiments/roi-switch-long \
  --pipeline24 --write-node port
```

`--write-node port` — экспериментальный путь именно для MV-AX5F57MP050E:
четыре байта Big Endian пишутся по адресу 0x3001002C, установленному из
XML подключённой камеры (ImageFormatControlBase + OffsetYReg). Применять
этот адрес к другой модели или прошивке без сверки XML нельзя. Допустимые
значения дополнительно ограничены четырьмя проверенными координатами;
геометрия и размер DMA-буферов во время потока не меняются. После теста
восстановление OffsetY проверяется также прямым чтением физического регистра.
`--write-node OffsetYReg` проверяет целочисленный узел регистра через GenApi;
по умолчанию используется стандартный узел `OffsetY`.

В обычном API OffsetY заблокирован при работающем потоке. Нативный тест
снимает локальную блокировку TLParamsLocked, сохраняя размер кадра. Это
проверенный экспериментальный способ для текущей камеры/SDK, а не
документированная производителем гарантия динамического ROI. Секвенсор
из полученного XML не включает OffsetY, поэтому тест его не использует.

Контроллер не воспроизводит накопившиеся запросы для уже прошедших кадров:
после задержки отсчитывает следующую границу от фактически принятого кадра.
Строгое число кадров каждой зоны проверяется по изображению; возможные
сбои расписания отражены в длинах серий и пропусках, а не скрываются.
В первых сохранённых сериях использован первоначальный вариант контроллера,
который накапливал просроченные границы; в series-port-long-01 — исправленный.

Проверка альтернативы: полный кадр и четыре ROI в оперативной памяти:

```bash
python3 scripts/run_roi_switch.py --out experiments/roi-fullsplit --fullsplit
```

Снимаются 512 кадров 7008×7000 без копирования и 512 с упаковкой четырёх
ROI 7000×1750 в один переиспользуемый буфер, с отбрасыванием 8 столбцов.
Это четыре области одной экспозиции, без последовательного сдвига окна.

В начале теста снимается эталон полной высоты. Из каждой четверти строится
пространственный профиль 64×32 (с усреднением площадок 8×8 пикселей).
Во время съёмки сравнивается изображение, поскольку значение OffsetY в
метаданных может соответствовать текущей настройке, а не содержимому буфера.
В тесте требуется неподвижная различимая сцена; на иной сцене профили могут
не разделяться. Неизвестные зоны и ошибки распознавания показаны в отчёте.
Этот классификатор предназначен для измерения, а не для маркировки произвольного
производственного видеопотока. Камера не предоставила ChunkModeActive.

Скрипт собирает `build/roi_switch_bench`, сохраняет журнал, начальные настройки
и CSV каждого кадра/переключения. В конце автоматически создаются report.md
и summary.csv. Отчёт можно повторно собрать без камеры:

```bash
python3 scripts/report_roi_switch.py experiments/roi-switch-my-run
```

Исходные параметры восстанавливаются и проверяются чтением, включая
TLParamsLocked. SIGINT/SIGTERM завершают тест с восстановлением; SIGKILL,
отключение питания и авария процесса такую гарантию дать не могут.
Нативный диагностический `roi_switch_probe.cpp` дополнительно показывает
блокировку стандартного API и расхождение метаданных с изображением; он
сохраняет XML в фиксированный каталог experiments/roi-switch-20261113.

[Результаты эксперимента 2026-11-13](../experiments/roi-switch-20261113/report.md).
